## 1. Timing

### Where the time goes

The base suite has 473 test files. A serial run of the non-golden lane (`flutter test --no-pub --concurrency=1 --exclude-tags golden`, JSON reporter) took 702.6 s wall and reported 6,432 passed and 22 skipped:

| Part | Seconds | Share |
|---|---|---|
| Loading and compiling test files | 334.1 | 48% |
| Test bodies | 360.0 | 52% |
| of which widget tests without a database | 156.7 | |
| of which unit tests with SQLite | 98.6 | |
| of which unit tests without a database | 77.1 | |
| of which widget tests with SQLite | 27.6 | |
| of which 34 tests ≥ 0.9 s (mostly real timers) | 88.1 | |

Compiling is half of the serial time. That is why file-level sharding pays and `flutter test --total-shards` does not: Flutter passes that flag to `package:test`, which splits the tests inside every file, so each shard would still compile all 473 files (`packages/flutter_tools/lib/src/test/runner.dart:89–90`).

`pumpAndSettle` appears 2,702 times under `test/` at the base. None of the slowest tests is dominated by it; the long tests wait on real time. The dominant real waits:

- ZeTime: `ZeTimeAdapter._replyWindow` is a fixed 5 s (`lib/ble/adapters/zetime.dart:38`). Six tests wait it out: 30.2 s serial.
- BLE blocker probe: `BleEngine._blockerProbe` is a fixed 2 s (`lib/ble/ble_engine.dart:2230`). `ble_blocker_engine_test.dart` spends 17.2 s, and single tests take 6.0 s, 4.0 s and 2.0 s.
- `openband_g3_live_durability_test.dart:137` waits a real 5 s for a liveness expiry.
- `alarm_test.dart:641,652` take 2.0 s and 4.0 s; `gen5_wiring_test.dart:721,733` 2.0 s each.

Making those windows injectable would remove about 70 s of serial time. Those files belong to Reliability and Code quality, so this audit lists them instead of changing them. With four files per runner in parallel, they no longer set the critical path.

Other sessions were running Flutter on the same machine during the base measurement; treat the local serial numbers as ±25% and the hosted numbers as the comparison. One earlier serial after-run stopped after 179 files because flutter_tools' own per-test temporary directory (`$TMPDIR/flutter_tools.*/flutter_test_listener.*`) vanished during finalization; nothing in this repository deletes those directories, and the rerun completed.

Concurrency was already passing at the base, but only by convention: all files open their databases in the shared `.dart_tool/sqflite_common_ffi/databases` directory, so two files that ever chose the same `LocalDb.dbName` would share a database when run together. No such pair was found; nothing prevented one. `test/flutter_test_config.dart` now points the shared FFI factory at a fresh temporary directory per test process (each test file is its own process), so concurrent files cannot share a SQLite file. The CI comment that justified `--concurrency=1` ("parallel workers race on them") no longer applies. After the change, three local runs at concurrency 8 and four hosted runs at concurrency 4 per shard passed with no failure; a fifth hosted run exposed the wall-clock race in finding 17, which is fixed. A first full-suite loop at concurrency 8 under load then exposed finding 18. After that fix, five consecutive full non-golden runs at concurrency 8 under the same load passed: all 473 files and 6,430 tests each, 721–767 s per run.

The golden job first loaded all 473 files to find the 65 that hold golden tests; locally that was 962 s of load time against 91 s of test bodies. It now loads only the files `tool/golden_test_files.sh` lists, the test files that call `matchesGoldenFile`, and runs every test in them, tagged or not, with the exact comparator. The script fails if `matchesGoldenFile` appears in any other tracked Dart file, because a shared helper's callers cannot be found by name. Its test step dropped from 236–280 s to 128–130 s. The Ubuntu shards run every test, golden ones included, with the accepting comparator, so every assertion runs somewhere and every pixel comparison is checked on macOS 27; tags only matter for the quick local `--exclude-tags golden` loop. The Ubuntu shards (about 4 minutes each, including 15–30 s of Flutter setup) are now the critical path; a fourth shard would save well under a minute.

## 2. Flakes

### `oura_link_test`

Hosted evidence: run 36757340369 (`4c4fb87b`) failed "the anchor and the cursor both survive the session" (`Expected: <1001>, Actual: <null>` at `test/oura_link_test.dart:194`) and "a reading held before the anchor arrives is written once it does" (`Actual: []` at `:230`). The log shows the batch commit landing (`decoded_archive_committed`, `cursor_advanced`) and no `oura_cursor_ds` note afterwards.

Reproduction: 20 plain runs and 20 runs under 14 CPU burners passed. With six processes writing and fsyncing 8 MiB in a loop plus ten CPU burners, 4 of 20 runs failed, on exactly the two tests and with the same assertions as on CI.

Root cause, from `lib/ble/oura_link.dart` and `lib/ble/adapters/oura.dart`:

1. `ingestForTest` passed its 50 ms test timeout as the adapter's `confirmTimeout` (production: 30 s). The adapter yields an `OffloadCheckpoint` and waits for `confirm()`; the host calls `confirm()` only after its real SQLite commit (`BandHost._commitThenConfirm`). A commit slower than 50 ms made the adapter log "batch was not confirmed", return without advancing the cursor, and never request the next batch. That is both failures.
2. `ingestForTest` spun 800 zero-duration event-loop turns and then closed the link, whether or not the session had ended. On a slow host the spin ends while a batch still waits on its commit, and a closed link refuses the next history request.
3. It cleared `_deviceId` without waiting for queued cursor writes, which read `_deviceId` when they run. `stop()` already waits for them.

Fix (test seam only, production paths unchanged): keep the adapter's default confirm timeout, await the session with a 30 s bound, then close the link, and wait for queued cursor writes before clearing state. After the fix, 20 consecutive runs of all 55 affected files under the same load passed (350 tests per run, 0 failures).

### `device_alerts_test`

Hosted run 36804428953 failed one test that had passed in every earlier run: "DeviceAlerts charging a failing sink still lets the announcement persist" (`Expected: <0>, Actual: <1>` at `test/device_alerts_test.dart:376`). The test delivers the same chargingOn twice, before and after a simulated restart, and computed its timestamp with `tsAged(3)` (wall clock minus 3 s) separately for each delivery. `ChargeAlertPolicy.evaluate` treats a session as already announced only when `ts <= lastAnnouncedEventTs`, so when the two reads land in different seconds the replay is a newer session and announces. Running files four at a time on a loaded runner made that second boundary likelier; it could also happen serially. The test now takes one timestamp for both deliveries, which is what it describes; the assertion is unchanged. The other tests in that file already reuse one timestamp. Twenty runs under load after the fix: 0 failures.

### Fixed-count waits on real SQLite work

The first full-suite run at concurrency 8 under load failed `ui2_revision_reload_test.dart` "water logged underneath the live route reaches it": `Found 0 widgets with text "750"` at line 175, followed by `tearDownAll` timing out after 12 minutes on the read the failure abandoned. Its `_until` helper gave the route's real SQLite reads 60 turns of 20 ms (1.2 s) to land. The same shape appeared in five more places: `pair_sensor_test.dart:170` (1.2 s), `ui2_wellness_recovery_paint_test.dart:202` (0.8 s, with a comment warning that a fixed duration is a flake) and three loops in `openband_journal_editor_test.dart` (2 s each). `test/support/real_async.dart` now provides `untilReal`, which repeats a test's own step until its condition holds or 30 s pass; each site keeps its step and assertions. `workout_reliability_test.dart` already used this deadline shape.

## 3. Value

Method: a static scan of all 473 test files and the review flow (6,325 `test`/`testWidgets` declaration sites), with manual checks of each candidate.

- **Tests without an assertion:** 6 executable declarations have no `expect`. Three rely on the framework's own failure oracles (pending timers, overflow, uncaught exceptions) and pin past crashes: `app_state_regressions_test.dart:674`, `ui2_day_steps_test.dart:101`, `route_tracker_test.dart:606`. Three only prove that a call does not throw: `app_state_notification_apply_test.dart:261,280,288`. None was removed; the last three could become one table-driven test.
- **Render-only tests:** 22 candidates assert only `takeException()` or the root widget. 18 are overflow or unmount-safety checks at large text or during in-flight loads, which are real regressions in this repo (`AGENTS.md` §4.5). Kept.
- **Duplicates:** two coach SQL guard cases were byte-identical across two files and are removed from the adversarial file. Other repeated bodies (adapter contract tests, cycle unmount tests) run against different adapters or screens and stay; a shared parameterized contract would cut code, not coverage.
- **Dead tests:** four golden groups had no masters and were skipped in every clone (408 skipped tests); removed with their now-unused fixtures. The non-golden tests in those files stay. `HomeScreen` and `HealthScreen` are still tested but no production route builds them (finding 12, Code quality owns the screens).
- **Goldens without a test, tests without a golden:** 666 masters under `test/openband_goldens/`. 567 are referenced by a literal name; the other 99 come from interpolated names. The static scan found no unreferenced master and no literal reference to a missing one. A proof that covers interpolated names would come from running the golden lane with `--update-goldens` in a clean checkout and diffing the file list; not done here.

## 4. Goldens in CI

The masters use the bundled Inter and Inter Tight fonts (`FontLoader` in each golden test), not Helvetica Neue. Helvetica Neue is used only by the Paper comparison tools (`tool/g2_review.py`, `tool/g3_review.py`), which extract it from macOS and never commit it. Font availability was never the blocker; host rasterization was.

Measured drift of the committed masters:

| Host | Result |
|---|---|
| Ubuntu (`ubuntu-24.04`, run 35873138903) | 533 failed; median 2.42%, p95 5.98%, max 42.99% of pixels |
| `macos-latest` (recorded in the previous workflow) | 544 failed, 0.03–0.58% |
| `xcode-27` (macOS 27 arm64, image 20260921.0210.1, run 36780041597) | 381 passed, 0 failed, exact comparison |

A tolerance comparator is not a safe substitute: one changed digit in a 393 × 852 capture is about 0.04% of its pixels, well inside the macOS drift. Rendering the masters in a Linux container and comparing on Ubuntu would work too, but it would replace all 666 masters with FreeType renders and require Docker for every local golden update.

Recommendation, implemented: compare pixels on `xcode-27` with the exact comparator on every pull request, running every test in the files that call `matchesGoldenFile`, and keep running all test bodies, golden ones included, in the Ubuntu shards with the accepting comparator.

Risk: `xcode-27` is a public-preview image. An image update that changes text rasterization would turn the golden job red without a code change. See Decisions for Mats.

## 5. The review flow

The base file was one `testWidgets` of 22,804 lines: shared helpers as closures, 25 `reviewX` closures, a flow dispatch on `OPENBAND_REVIEW_FLOW`, and the inline `all` sequence.

It now stays a single entry point, because every integration-test file costs its own iOS build in `tool/ui_review.py`. The entry file (82 lines) maps flow names to functions. `integration_test/review/harness.dart` holds the shared helpers on `ReviewHarness`; each area is a part file of that library (largest 1,445 lines) so private fixtures keep their names. The move is mechanical: a token comparison against the base file finds 994 of 994 capture sites (899 literal names, 95 computed), 2,649 of 2,649 `expect` sites, the same 28 flow names, and the same order for the 16 sections of `all`.

Simulator runs after the split (`python3 tool/ui_review.py capture`, synthetic data only):

| Flow | iPhone 15 Pro | iPhone 13 mini | Base (`61dcdd29`), same flow |
|---|---|---|---|
| `release` (the default) | passed, 64 captures, 182 s | passed, 64 captures, 203 s | not rerun |
| `journal-hub`, `sleep-plan`, `temperature`, `weight` | passed; 46, 23, 21, 28 captures | not run | not rerun |
| `all` | failed at its first overview tap after 1 capture | failed identically | failed identically, same capture set |

Every flow that fails after the split fails on the base at the same step with the same captures, and `release` passes on both phone sizes; the four other passing flows were not rerun on the base. The 22 failing flows (21 plus `all`) are finding 7; they were already broken on the base. Their first failures are missing labels, changed counts or a vanished semantics label, for example `integration_test/review/journal.dart:303` (a "Entwurf behalten" button that no longer exists) and `review/correction.dart:42` (the `Schlaf, …` overview label). ## Decisions for Mats

1. **Golden masters and the preview runner.** Masters are baked on your Mac (macOS 27.0) and now checked on GitHub's `xcode-27` preview image; today they match exactly. If either side changes its macOS minor version, the golden job can go red with no code change. Options: (a) keep the job required and rebake on whichever side moved, (b) make the runner the source of truth with a manual workflow that renders masters on `xcode-27` and uploads them as an artifact, (c) make the golden job advisory. Recommendation: (a) now, (b) if it happens twice.
2. **The 22 broken review flows.** Only `release`, `journal-hub`, `sleep-plan`, `temperature` and `weight` pass today. Most of the others walk development-only areas (nutrition, cycle, medication, labs), and all of them fail at the first stale label, so each hides an unknown number of later stale steps. Options: (a) re-author the flows for release-scope screens against the current G3 UI and delete the ones for development-only areas, (b) re-author all 22, (c) delete them. Each fix needs simulator iterations of 40–80 s per attempt. Recommendation: (a), and afterwards run every remaining flow in one scheduled job so they cannot rot silently again.
3. **Real-time windows in BLE code.** Injectable reply and probe windows (ZeTime 5 s, blocker probe 2 s) would cut about 70 s of serial test time and remove the last real-time races in those tests. It changes `lib/ble`, so it belongs to the reliability work, not this PR.

## What this audit does not prove

- Hardware: no test here touches the phone, the band or Bluetooth. Every number is from the Flutter test host or the iOS simulator with synthetic data.
- The flake fix is proven by loops on one machine under synthetic load and by hosted runs; a rare CI-only interleaving could still exist.
- Coverage findings come from reading tests, not from a coverage tool.
- The golden lane matching `xcode-27` is proven for image 20260921.0210.1 only.

## Appendix: method

- Timing: `flutter test --file-reporter=json:…`, summarized per file and per test; `loading` pseudo-tests are the compile/load time.
- Loops: one Flutter process at a time; load generator: six processes writing and fsyncing 8 MiB in a loop plus ten `yes` processes.
- Static value scan: brace-matching scan of every test declaration, import-graph reachability from `lib/main.dart` and `lib/app.dart`, golden reference matching, and literal-finder counts.
- Split proof: token-order comparison of every moved body against the base file.
- The scan, loop and timing scripts were one-off audit tools and are not committed; the commands above reproduce the measurements.
